### Сайн сценариогийн 5 шинжээр өөрийгөө шалгасан нь

- Итгэмжтэй: ачаалал, алдааны түвшин нь серверийн бодит зан төлөвтэй таарна (жишээ нь /pay-д 5% алдаа суулгасан).
- Үнэ цэнэтэй: хэрэглэгчийн хамгийн чухал үйлдлүүд (сагс, төлбөр, тайлан) болон зогсолтыг хамарсан.
- Тодорхой: өдөөлт, орчин, ачаалал (VU, хугацаа) тус бүр нэрлэгдсэн.
- Нарийн: хэмжүүр бүр тоон босго, магадлалын хэлбэртэй (p95, хувь).
- Ойлгомжтой: 6 хэсэгтэй хүснэгтээр тогтмол бичигдсэн.

## 2. SLO хүснэгт

| Сценарио | SLI (юуг хэмжих) | Босго | Цонх / нөхцөл |
| --- | --- | --- | --- |
| Performance | /cart/add latency | p(95) < 50 мс | 20 VU тогтмол ачаалалд, 1 мин |
| Reliability | /pay error rate | rate < 0.08 (8%) | 20 VU, 1 мин |
| Availability | Бүх хүсэлтийн амжилтын хувь (checks) | rate > 0.90 (90%) | 2 мин, ойролцоогоор 10 с зогсолттой |
| Report (нэмэлт) | /report latency | p(95) < 450 мс | 20 VU, 1 мин |

Эдгээр босго `slo-test.js` доторх threshold-той яг ижил:
`http_req_duration{name:cart}` p(95)<50, `http_req_failed{name:pay}` rate<0.08, `checks` rate>0.90, `http_req_duration{name:report}` p(95)<450.

### Босго сонгосон үндэслэл

- Cart p(95) < 50 мс: localhost дээр /cart/add ойролцоогоор 1 мс-д хариулдаг тул заавраар өгсөн 200 мс нь юу ч хэмжихгүй сул босго болно. 50 мс нь бодит хариу хугацаанаас хол зайтай боловч ноцтой удаашралыг барьж чадна.
- Pay rate < 0.08: серверт ойролцоогоор 5% алдаа суулгасан тул 8% нь бодитой босго.
- Availability > 0.90: 2 минутын цонхонд богино зогсолтыг зөвшөөрөх түвшин.
- Report p(95) < 450 мс: endpoint зориуд 200-400 мс хүлээдэг тул 450 мс нь дээд хязгаараас бага зэрэг дээгүүр зай үлдээнэ.

### Error budget тооцоо

- Цагаар: 2 минут × 10% = 12 секундийн "эвдрэх эрх".
- Хүсэлтээр: chaos тестийн нийт 5748 хүсэлтийн 10% = ойролцоогоор 575 хүсэлт алдаатай байж болно.

## 3. Тестийн үр дүн

### 3.1 Хэвийн тест (results/pass.txt)

| Хэмжүүр | Үр дүн | Босго | Дүн |
| --- | --- | --- | --- |
| cart p(95) | 1.45 мс | < 50 мс | PASS |
| report p(95) | 390.21 мс | < 450 мс | PASS |
| pay error rate | 5.28% (927 хүсэлтийн 49) | < 8% | PASS |
| checks | 98.23% (2781-ийн 2732) | > 90% | PASS |

### 3.2 Chaos тест (results/chaos.txt)

2 минутын тестийн явцад серверийг Ctrl+C-ээр зогсоож, ойролцоогоор 10 секунд хүлээгээд дахин асаасан.

| Хэмжүүр | Үр дүн | Босго | Дүн |
| --- | --- | --- | --- |
| checks (availability) | 83.80% (5748-ийн 4817 амжилттай) | > 90% | FAIL |
| http_req_failed (бүгд) | 16.19% (5748-ийн 931) | | |
| pay error rate | 18.99% (1916 хүсэлтийн 364) | < 8% | FAIL |
| cart p(95) | 1.37 мс | < 50 мс | PASS |
| report p(95) | 389.51 мс | < 450 мс | PASS |

Бодит availability = амжилттай хүсэлт / нийт хүсэлт = 4817 / 5748 = 83.80%. Энэ нь 90%-ийн SLO-оос доогуур. Алдаатай хүсэлт 931 болсон нь зөвшөөрөгдсөн ойролцоогоор 575-аас их тул error budget хэтэрсэн.

Зогсолтын үед cart-ын 1916 хүсэлтийн 281, report-ын 1916-ийн 286, pay-ийн 1916-ийн 364 нь амжилтгүй болсон. Cart-д зориуд суулгасан алдаа байхгүй тул түүний 281 алдаа нь зөвхөн зогсолтоос үүдэлтэй. Pay-ийн алдаа зогсолт дээр нэмэх нь суулгасан 5%-ийн алдаа тул арай их байна.

### Цагийн budget ба хүсэлтийн budget яагаад зөрж байна вэ

Цагаар тооцсон 12 секундийн budget нь хугацаа, харин k6-ийн checks нь хүсэлтийн хувийг тоолдог. Сервер унасан үед хүсэлт агшин зуур (connection refused) буцдаг ба /report-ын 200-400 мс хүлээлт алга болдог. Иймээс зогсолтын нэг секунд хэвийн секундээс олон хүсэлт "иддэг". Нэмж хэлэхэд, серверийг гараар зогсоож дахин асаахад төлөвлөсөн 10 секундээс арай урт хугацаа зарцуулагдсан байж болно. Эдгээр хоёр шалтгаанаар хүсэлтээр тооцсон алдаа (16.19%) нь цагаар тооцсон хувь (12 с / 120 с = 10%)-аас их гарсан. Хэвийн тестэд ч pay-ийн суулгасан алдаанаас болж checks-ийн 1.76% (2781-ийн 49) нь амжилтгүй байсан нь availability budget-ийн нэг хэсгийг зогсолтоос өмнө нэгэнт идсэн гэсэн үг.

### Нэг эвдрэл хоёр SLO-г зэрэг зөрчсөн нь

Сервер унасан үед /pay-ийн хүсэлт бүр унадаг тул availability болон reliability хоёр SLO зэрэг FAIL болсон. Тэдгээрийг тусгаарлахын тулд availability-д зөвхөн хариу ирээгүй (connection error) хүсэлтийг, reliability-д зөвхөн сервер ажиллаж байхад ирсэн HTTP 500 хариуг тоолох хэрэгтэй.

### 3.3 Зориуд FAIL болгосон тест (results/fail.txt)

`slo-test-fail.js` дотор /report-ын threshold-ыг p(95)<100 болгосон. Сервер 200 мс-ээс хурдан хэзээ ч хариулдаггүй (бодит p(95) = 387.75 мс) тул `http_req_duration{name:report}` threshold FAIL болж, k6 `exit=99` exit code буцаасан. CI pipeline яг энэ ойлгомжтой exit code-оор build-ийг зогсоодог. Харин /cart/add-ыг p(95)<50 болгоход localhost дээр PASS хэвээр үлддэг, учир нь бодит хариу хугацаа нь ойролцоогоор 1 мс.

## 4. Дүгнэлт

Сценарио → SLO → threshold шилжилтэд хамгийн хэцүү нь тодорхой бус хүслийг жинхэнэ утгатай тоон босго болгох явдал байсан. Жишээ нь localhost дээр /cart/add 1.45 мс-д хариулдаг тул заавар дахь 200 мс-ийн босго юуг ч хэмжихгүй байсан бөгөөд би 50 мс-ийг сонгосон. Хэвийн тестэд дөрвөн threshold бүгд PASS болж, pay-ийн алдааны хувь 5.28% буюу суулгасан 5%-тай ойр гарсан. Chaos тестэд ойролцоогоор 10 секундийн зогсолт availability-г 83.80% болгож, 90%-ийн SLO-г зөрчсөн. Цагаар тооцсон 12 секундийн budget нь k6-ийн хүсэлтээр тооцдог хэмжүүрээс өөр дүн өгсөн, учир нь зогсолтын үед хүсэлтүүд агшин зуур алдаа буцаадаг. Нэг эвдрэл availability болон reliability хоёр SLO-г зэрэг зөрчсөн тул ирээдүйд хоёр SLI-гээ тусгаарлаж, connection error болон HTTP 500-г өөр өөрөөр тоолох хэрэгтэй. Зориуд FAIL тест нь threshold нь автоматаар build зогсоох хаалга болдгийг exit code 99-өөр харуулсан. Тиймээс chaos туршилт миний availability сценариогийн хэмжүүрийг "үгүйсгэсэн": 90%-ийн босго ба 10 секундийн зогсолт хоёр зэрэг боломжгүй байсан. Дараагийн удаа би зогсолтын хугацааг богиносгох эсвэл SLO-гоо цагийн цонхоор тодорхойлох байсан. Мөн сэргэх хугацааг k6 шууд хэмждэггүй тул түүнийг тусад нь хэмжих хэрэгтэйг ойлгосон.
